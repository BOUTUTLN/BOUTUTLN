## 2. 주문 실행 설계

### 2.1 주문 상태 머신 [제안]

```
 DRAFT ──리스크 승인──▶ APPROVED ──DB 기록 후 전송 시작──▶ SUBMITTING
                                                          │
          ┌───────────────── 응답 수신(주문번호) ◀──────────┤
          ▼                                               │ 시간 초과·연결 끊김·
      ACKNOWLEDGED ──일부 체결──▶ PARTIALLY_FILLED          │ 알 수 없는 응답
          │  │                        │                    ▼
          │  └─────── 전량 체결 ──────┴──▶ FILLED        UNKNOWN ──조회로 확인──▶ ACKNOWLEDGED / NOT_FOUND
          │                                                                     │
          ├──취소 요청──▶ CANCEL_PENDING ──▶ CANCELLED (부분 체결분은 유지)        └▶ (유예 후 재조회) FAILED_NOT_SENT
          ├──거부──▶ REJECTED
          └──장 마감──▶ EXPIRED
```

- 모든 상태 전이는 DB 트랜잭션으로 기록하고, 전이 이력을 남깁니다.
- 허용되지 않은 전이(예: FILLED → CANCELLED)는 코드에서 예외를 냅니다.
- 최종 상태: FILLED, CANCELLED, REJECTED, EXPIRED, FAILED_NOT_SENT

### 2.2 내부 주문 ID와 중복 방지 통제 [v0.4 기본 설계]

> **KB증권 API는 사용자 지정 주문 ID를 지원하지 않으므로 [확인], 브로커 수준의 멱등성(같은 요청을 다시 보내도 주문이 한 번만 접수되는 기능)은 없습니다.** 아래 장치는 시스템 내부에서 **중복 주문을 만들 가능성을 줄이고, 생겼을 때 빨리 감지**하기 위한 통제입니다. 모든 장애 상황에서 중복 주문이 없다고 보장하지는 못합니다.

- **내부 주문 ID** `intent_id` = (장부, 리밸런싱 실행 ID, 종목, 매수/매도, 분할 순번)으로 결정되는 값. DB에 유일성 제약을 겁니다. 같은 리밸런싱을 다시 실행해도 같은 ID가 나오므로, 시스템이 같은 주문 의도를 두 번 만드는 것을 막습니다. 이 ID는 KB에 전달되지 않습니다.
- **송신 전 기록(outbox 방식)**: `SUBMITTING` 상태를 먼저 커밋한 뒤 HTTP 요청을 보냅니다. 프로세스가 중간에 죽어도 "보냈을 수도 있는 주문"이 DB에 남습니다.
- **종목당 활성 주문 1개**: 같은 장부·같은 종목에 최종 상태가 아닌 주문이 있으면 새 주문을 만들지 않습니다. 응답이 유실됐을 때 조회 결과에서 찾아야 할 주문 후보를 하나로 좁혀 줍니다.
- **주문 API는 자동으로 다시 보내지 않습니다.** 조회 API만 재시도합니다.

### 2.3 응답 유실 처리 규칙 [v0.4 기본 설계]
주문 전송 후 시간 초과, 연결 끊김, 해석할 수 없는 응답이 생기면 아래 순서를 **반드시** 따릅니다.

1. **상태를 `UNKNOWN`으로 변경**하고 전송 시각, 요청 내용, 받은 응답(있으면)을 기록합니다.
2. **해당 종목의 신규 주문을 차단**합니다(같은 장부의 같은 종목. 정정·취소 요청도 보류).
3. **미체결 및 체결 내역을 조회**합니다(국내 SSQM2341, 해외 SPQM2204, 모두 조회 API [확인]).
   - 찾는 조건: 주문일자, 종목, 매수/매도, 수량, 가격, 주문 시각이 전송 시각 ± N초 이내, 내부 DB에 아직 연결되지 않은 주문번호
   - 국내 조회 결과에는 주문시간(`ordr_tm`), 주문매체코드(`ordr_md_cd`), 원주문번호가 있음 [확인]
4. **계좌 잔고와 내부 장부를 대조**합니다(보유수량, 해당 통화 예수금, 주문가능금액 변화). 주문 내역 조회 결과와 잔고 변화가 서로 맞는지 함께 봅니다.
5. **주문 여부가 확인되기 전에는 절대 자동으로 다시 보내지 않습니다.**
6. 판정
   - 조건에 맞는 주문이 정확히 1건이고 잔고 변화와도 맞음 → 주문번호를 연결하고 `ACKNOWLEDGED` 이후 상태로 진행
   - 조건에 맞는 주문이 없고 잔고 변화도 없음 → 유예 시간(예: 30초) 뒤 한 번 더 조회·대조 → 그래도 없으면 `FAILED_NOT_SENT`. 이 주문 의도는 **다음 리밸런싱에서 새로 계산**할 때만 다시 만들 수 있음(같은 실행 안에서 바로 재전송하지 않음)
   - **확인할 수 없음**(후보가 2건 이상, 조회 실패, 조회 결과와 잔고가 서로 맞지 않음) → **해당 장부의 거래를 중단(L2 Book Halt)**하고 긴급 알림을 보냄. **사람이 KB 앱이나 HTS로 직접 확인하고 수동으로 상태를 확정하기 전까지 거래를 재개하지 않음**

### 2.3.1 실시간 모의투자 프로세스에서의 적용
- 페이퍼 엔진은 내부 엔진이므로 응답 유실이 실제로는 생기지 않지만, 같은 규칙을 시험하기 위해 **장애 주입 테스트**로 응답 유실을 일부러 만들어 위 절차를 검증합니다.

### 2.4 미체결·부분 체결 처리 [제안]
- 일 1회 리밸런싱: 주문 후 일정 시간(예: 30분)마다 미체결을 확인합니다. 정해진 횟수까지는 가격을 한 틱씩 조정(정정)하고, 그래도 안 되면 장 마감 전에 취소합니다.
- 부분 체결분은 그대로 유지하고, 남은 수량은 다음 리밸런싱에서 다시 계산합니다(억지로 다 채우지 않음).
- 정정·취소 요청 자체가 실패하거나 결과 불명이면 위 2.3과 같은 절차로 처리합니다.

### 2.5 서버 재시작 후 복구 [제안]
1. 재시작하면 항상 **SAFE 모드**(신규 주문 금지)로 시작
2. DB에서 최종 상태가 아닌 주문을 모두 불러옴
3. 브로커(페이퍼 모드는 페이퍼 엔진)에서 당일 주문·체결과 잔고를 조회(미국은 날짜 경계 때문에 전일분도 포함)
4. 주문별로 상태를 맞추고(2.3 매칭 규칙 사용), 장부 대사(§3)를 수행
5. 모두 일치하면 NORMAL 모드로 전환하고, 하나라도 불일치하면 HALT 상태를 유지하고 알림
6. 운영 서버 재부팅 시 컨테이너와 서비스가 자동 시작되도록 구성(systemd 또는 Docker restart 정책)

## 3. 잔고 대사 (Reconciliation)

### 3.1 대상과 주기 [제안]

| 시점 | 대상 |
|---|---|
| 체결 이벤트 직후 | 해당 종목 수량 |
| 각 시장 장 마감 후 | 전체 보유 종목·수량, 통화별 예수금, 미체결 주문 |
| 서버 시작 시 | 전체 |
| 매주 | 실현손익·수수료·세금(KB 손익 조회 API와 비교) |

사용 API(모두 조회 API) [확인]: 국내 SSQM2952·SSQM1801(잔고), SSQM0004(예수금), SSQM2341(체결/미체결) / 해외 SPQM2226(잔고평가), SKQM3350(통화별 예수금), SPQM2204(체결/미체결), SRQM3051(권리)

### 3.2 판정 기준 [제안]
- 수량: **정확히 일치**해야 함(소수점 주식은 소수 6자리까지)
- 현금: 허용 오차 안이면 일치(예: KRW 10원, USD $0.05). 반올림이나 수수료 차이로 생기는 차이는 원인을 기록하고 장부를 보정
- 불일치 유형과 조치

| 유형 | 예시 | 조치 |
|---|---|---|
| 설명 가능한 차이 | 배당 입금, 수수료 반올림 | 자동 보정 + 기록 |
| 외부 활동 | 사용자가 MTS로 직접 매매, 직접 환전, 입출금 | 해당 장부 **HALT**, 사람이 확인한 뒤 "외부 이벤트"로 등록 |
| 설명 불가 | 내부에 없는 체결, 수량 차이 | 해당 장부 **HALT**, 알림 |

- 대사 성공률 = (불일치 없이 끝난 대사 횟수 / 전체 대사 횟수). 실거래 승인 기준에 사용합니다(PLAN 11장).
- **v0.4 확정**: KB증권 **단일 계좌**를 우선 지원합니다. 한 계좌 안에서 KRW 장부와 USD 장부를 논리적으로 완전히 분리하고, 대사는 통화별로 따로 합니다. 이 계좌에서는 사용자가 직접 매매·환전하지 않는 것을 원칙으로 하며(자동매매 전용 계좌 권장), 직접 활동이 감지되면 외부 이벤트로 처리하고 해당 장부를 정지합니다.

### 3.3 페이퍼 모드의 대사
- 페이퍼 모드에서는 "브로커"가 페이퍼 엔진이므로 내부 장부와 페이퍼 엔진 사이의 대사를 같은 코드로 수행합니다(코드 경로 검증 목적).
- 추가로 KB 실계좌의 **조회 API 응답 형식**이 파서와 맞는지 매일 확인합니다(계좌 잔고 금액은 사용하지 않음).

## 4. API 오류·네트워크·데이터 품질

### 4.1 오류 분류와 처리 [제안]

| 분류 | 판단 기준 | 조회 API | 주문 API |
|---|---|---|---|
| 네트워크·시간 초과 | 연결 실패, 응답 없음 | 지수 백오프로 재시도(최대 N회) | 재시도 금지 → `UNKNOWN` |
| 인증 오류 | 토큰 만료, 권한 오류 | 토큰 재발급 1회 후 재시도 | 재발급만 하고 주문은 다시 확인 절차 |
| 호출 제한 초과 | 가이드에 나온 "호출 제한 초과" | 대기 후 재시도, 제한기 속도 낮춤 | 재시도 금지, 다음 주기에 다시 판단 |
| 업무 오류 | HTTP 200 + `o_clsf`/`o_msg`가 실패 | 재시도 안 함, 기록 | `REJECTED` |
| 알 수 없는 응답 | 파싱 실패, 필드 누락 | 재시도 1회 후 실패 처리 | `UNKNOWN` |
| 서버 점검·장애 | 5xx, 연속 실패 | 서킷 브레이커 열림 | 신규 주문 차단 |

- 서킷 브레이커: 5분 안에 조회 실패율이 30%를 넘으면 신규 주문을 차단하고 알림을 보냅니다. 연속 성공이 확인되면 반쯤 열린 상태를 거쳐 복구합니다.
- 토큰: 유효기간 24시간 [확인]. 만료 1시간 전에 미리 재발급합니다.
- 응답의 숫자는 문자열이고 단위 규칙(P4 등)이 있습니다 [확인]. `Decimal`로만 변환하고, 필드별 단위 규칙은 명세에서 생성한 스키마로 관리합니다.

### 4.2 시세 지연·이상 감지 [제안]
- **신선도**: 시세 시각(국내 체결시간, 미국 `kor_tm`)과 현재 시각의 차이가 기준(예: 국내 10초, 미국 15초)을 넘으면 "오래된 시세"로 표시
- **지연 시세 플래그**: 미국 시세구분이 지연(`1`)이면 모의 체결과 실주문을 모두 중단 [필드 존재 확인]
- **이상치**: 직전 대비 급변(예: 15% 이상)인데 지수 움직임과 관계없을 때, 매수호가가 매도호가보다 높을 때(호가 역전), 0 또는 음수 가격, 거래량 0인데 가격 변동
- **교차 검증**: 장 마감 후 KB 종가와 보조 데이터 공급자 종가를 비교(허용 오차 초과 시 기록)
- **조치**: 해당 종목 신규 주문 차단. 시장 전체 이상이면 해당 장부 Soft Halt

## 5. 비상 정지(킬 스위치) 정책

> 원칙: **킬 스위치가 발동해도 보유 종목을 자동으로 전량 매도하지 않습니다.** 기본 동작은 신규 주문 차단입니다. [제안]

### 5.1 단계

| 단계 | 범위 | 신규 매수 | 신규 매도 | 미체결 주문 | 해제 |
|---|---|---|---|---|---|
| **L1 Soft Halt** | 장부 1개 | 차단 | 리밸런싱 매도 차단, **손절 규칙 매도만 허용(설정)** | 미체결 매수 취소, 미체결 매도는 유지(설정) | 조건 해소 후 자동 또는 수동(설정) |
| **L2 Book Halt** | 장부 1개 | 차단 | 전부 차단(손절 포함) | 모두 취소 요청 | 수동만 |
| **L3 Global Halt** | 전체 | 차단 | 전부 차단 | 모두 취소 요청 | 수동만, 해제 사유 기록 필수 |

- 부분 체결된 주문은 체결된 수량을 유지하고 남은 수량만 취소합니다.
- 청산(전량 매도)은 **사람이 텔레그램이나 콘솔에서 명시적으로 명령하고, 한 번 더 확인했을 때만** 실행합니다.
- 취소 요청이 실패하거나 결과를 알 수 없으면 2.3 절차를 따르고, 해결될 때까지 HALT를 유지합니다.

### 5.2 발동 조건(초기값)

| 조건 | 단계 |
|---|---|
| 장부 일일 손실 −2% | L1 |
| 장부 누적 MDD −15% | L2 |
| 전체(원화 환산) 누적 MDD −12% | L1(양쪽 장부) |
| 대사 불일치(설명 불가·외부 활동) | L2 |
| 주문 결과 불명 미해결, 매칭 후보 여러 개 | L2 |
| 시세 지연·이상(시장 전체) | L1 |
| API 서킷 브레이커 열림 | L1 |
| 시장 급변(지수 장중 −3% 이상, VIX·VKOSPI 기준 초과) | L1(신규 매수만 차단) |
| AI 비용 한도 초과 | **매매는 계속**, AI만 끄고 정량 단독으로 전환 |
| 사람의 `/halt` 명령 | L3 |

## 6. AI Provider·비용 관리 설계

### 6.1 AI Provider 인터페이스 [제안]
```
AIProvider (인터페이스)
 ├─ analyze(request: AnalysisRequest) -> AnalysisResult   # 구조화 출력, 스키마 검증 포함
 ├─ estimate_cost(request) -> Money(USD)
 └─ capabilities() -> {models, max_context, supports_batch, supports_cache}

구현: ClaudeProvider (Anthropic SDK) / RecordedProvider (저장된 응답 재생, 테스트·백테스트용) / NullProvider (AI 끔)
```
- 거래 시스템은 `AnalysisRequest/AnalysisResult` 스키마만 압니다. 모델을 바꿔도 Provider 설정만 바뀝니다.
- 작업 종류별로 모델을 따로 지정할 수 있게 합니다(뉴스 요약/중복 판정, 종목 판단, 주간 리뷰).

### 6.2 비용 통제 [제안]

| 항목 | 설계 |
|---|---|
| 모델별 비용 기록 | 호출마다 API 응답의 사용량(입력·출력·캐시 토큰)과 단가표로 비용을 계산해 저장 |
| 종목별 비용 기록 | 호출에 종목·장부·전략(B/C)·작업 종류 태그를 붙여 집계 |
| 일·월 한도 | 예: 일 $3, 월 $60(사용자 결정). 80%에서 경고, 100%에서 AI 끔 → 정량 단독으로 전환. Anthropic 콘솔의 지출 한도도 함께 설정 |
| 중복 분석 방지 | 입력 해시(종목 + 데이터 스냅샷 + 프롬프트 버전 + 모델) 기준. 같은 입력이면 저장된 결과를 재사용 |
| 결과 캐싱 | 판단 결과는 유효기간(예: 다음 리밸런싱까지) 동안 재사용. 시스템 프롬프트에는 프롬프트 캐싱 적용 |
| 뉴스 중복 제거 | URL 정규화 + 제목·본문 유사도(MinHash 등)로 같은 사건의 기사를 하나로 묶은 뒤에만 요약 |
| 변화 기반 호출 | 전일 대비 새 공시·뉴스가 없고 점수 변화가 작으면 그 종목은 다시 분석하지 않음 |
| 배치 처리 | 일 1회 분석은 Batch API(50% 할인)를 우선 사용. 마감 시간 안에 결과가 오지 않으면 그날은 정량 단독 |
| 호출 실패 | 시간 초과·스키마 오류·거절 응답 → 1회 재시도 후 실패 시 해당 종목은 정량 비중 그대로(λ=0) |
| Fallback | `NullProvider`로 바꾸면 전체 시스템이 A(정량 단독)로 동작해야 하며, 이를 테스트로 보장 |

### 6.3 개발 비용과 운영 비용 구분 [v0.4 기본 설계]
- **개발용 Claude Code 사용(Claude Cloud 포함)**: 사용자의 Claude 구독 사용량 한도 안에서 쓰이고, 한도를 넘으면 사용자가 켠 경우 사용량 크레딧(종량제)으로 청구됩니다 [확인: Claude 요금 페이지·고객지원 문서]. Max·Team 플랜에 포함된 월간 API 크레딧은 대화형 Claude Code(웹 포함)에 쓰이지 않는다고 안내되어 있습니다 [확인: 고객지원 문서]. Claude Cloud 세션의 세부 계량 방식은 [미확인]입니다. 운영 시스템과 무관하고 개발 기간에만 발생합니다.
- **운영 AI API 비용**: 완성된 프로그램이 매일 호출하는 Anthropic API 비용입니다. Claude Code를 거치지 않고 Anthropic API를 직접 호출하며, **운영 전용 API 키와 별도 워크스페이스**로 분리해 청구서와 한도를 따로 관리합니다. 모의투자용·실거래용 키도 나눕니다. 운영 API 키는 운영 서버에만 둡니다.
- 비용 추정은 [개발 및 운영 비용 추정](development-cost-estimate.md) 문서에 있습니다.

## 7. 운영 환경과 보안

### 7.1 환경 분리 [v0.4 기본 설계]

| 환경 | 위치 | 용도 | 보관하는 비밀정보 |
|---|---|---|---|
| 개발 | **Claude Cloud 세션**, 개인 PC | 코드 작성, 단위 테스트, 녹화된 KB 응답으로 테스트 | **없음**(KB 키, 운영 AI 키 모두 없음) |
| 모의투자 | 운영 클라우드 서버의 **모의투자 서비스** | 데이터 수집, 페이퍼 엔진, A/B/C 그림자 장부 | KB 조회용 자격증명, 운영 AI API 키(모의투자용), 텔레그램 토큰 |
| 실거래(승인 전 미배포) | 같은 클라우드 인프라의 **실거래 서비스** | 승인 후 실거래 | KB 실거래용 자격증명, 실거래용 AI API 키 |

- **Claude Cloud 세션은 운영 서버로 쓰지 않습니다.** 컨테이너가 비활성 시 회수되고 [확인: 세션 환경 정보], 계속 실행된다는 보장이 없으며, 운영 비밀정보를 개발 도구에 두면 안 되기 때문입니다. 또한 개발 환경의 외부 IP가 해외로 판정되면 KB API 호출이 차단될 수 있습니다(§7.2).
- 운영 서버에는 Git 태그로 고정된 릴리스만 배포합니다. Claude(개발 도구)에게 운영 서버 접속 권한을 주지 않습니다.

**모의투자와 실거래의 격리 (C7)**
모의투자와 실거래는 같은 클라우드 인프라(같은 서버나 같은 계정)에 배포할 수 있지만, 아래 단위로 **완전히 분리**합니다.

| 분리 단위 | 모의투자 | 실거래 |
|---|---|---|
| 프로세스·서비스 | `paper` 서비스(컨테이너) | `live` 서비스(컨테이너). 승인 전에는 **배포하지 않음** |
| 데이터베이스 | `paper` DB(별도 PostgreSQL 데이터베이스와 계정) | `live` DB(별도 데이터베이스와 계정). 서로의 DB 계정 권한 없음 |
| 인증정보 | 모의투자용 비밀정보 파일 | 실거래용 비밀정보 파일. 모의투자 서비스에는 마운트하지 않음 |
| 실행 이미지 | **KB 주문 모듈을 포함하지 않고 빌드**한 이미지 | 주문 모듈 포함 이미지 |
| 설정 | `trading.mode=paper` 고정 | `trading.mode=live` + 승인 파일 |

**모의투자 프로세스가 실거래 주문 API를 호출할 수 없게 하는 장치**
1. 모의투자 이미지에는 KB 주문 API 클라이언트 코드가 들어 있지 않습니다(빌드 단계에서 제외하고, CI에서 이미지 내용을 검사).
2. HTTP 계층의 엔드포인트 허용 목록에 조회 API만 있습니다. 주문 API 경로(SSAM*, SKAM*, SPAO* 등)는 요청을 만들기 전에 거부합니다.
3. "paper 모드에서 주문 엔드포인트가 호출되지 않는다"는 테스트를 CI에 넣습니다.
4. 자격증명 분리: KB가 **조회 권한만 있는 앱키**를 따로 발급해 준다면 모의투자 서비스에는 그 키만 둡니다. 토큰 검증 항목에 "API 권한"이 있지만 [확인], 권한을 나눠 신청하거나 앱키를 여러 개 받을 수 있는지는 [미확인]입니다.
5. **남는 위험**: KB가 주문 권한이 포함된 앱키 하나만 발급한다면, 모의투자 서비스가 가진 자격증명은 기술적으로 주문할 수 있는 키입니다. 이 경우 1~3번(코드 부재, 허용 목록, 테스트)에 의존하게 되므로, 이 사실을 KB 답변을 받은 뒤 승인 기준(G5)에 명시합니다.

### 7.2 네트워크·IP 조건
상세: [KB API 조사 7장](kb-openapi-research.md)

- **해외 IP 차단 [확인]**: KB는 2026-10-28 공지로 해외 IP를 통한 오픈API 접속과 API 호출을 차단한다고 안내했습니다. 국내 IP는 기존처럼 이용할 수 있고, 해외 서버·VPN은 제한될 수 있습니다.
- **IP 화이트리스트(사전 등록)**: 공식 자료에 없습니다 [미확인]. 해외 IP 차단과는 별개의 문제입니다.
- **`ipAddr`/`macAddr`**: 헤더 필드 예시만 있고 값 기준·검증 방식은 [미확인].
- **클라우드 IP**: 국내 리전 IP를 국내로 판정하는지 [미확인]. AWS 서울 리전 IP도 판정 방식에 따라 해외로 분류될 가능성이 있다고 보고 [가정], 사전 접속 확인과 국내 클라우드 사업자 대안을 준비합니다.
- **고정 공인 IP**: 공식 요구사항은 없지만 헤더 일관성, 토큰 바인딩 가능성, 향후 등록제 가능성 때문에 권장합니다 [제안].

### 7.3 클라우드 서버와 로컬 PC 비교

| 항목 | 클라우드 VM(국내 리전) | 로컬 PC(집) |
|---|---|---|
| 고정 IP | 쉽게 확보(예: Lightsail은 고정 IP가 요금에 포함 [확인: AWS 요금 페이지]) | 가정용 회선은 대부분 유동 IP [가정] |
| 가동률 | 높음 | 정전·재부팅·회선 장애에 취약 |
| MAC 주소 | 인스턴스를 유지하면 일정할 것으로 예상, 교체하면 바뀔 수 있음 [가정] | 일정함 |
| 미국 장 시간(한국 밤) 운영 | 문제없음 | PC를 밤새 켜 둬야 함 |
| 비용 | 월 $12~24 수준(아래) | 전기료 외 추가 비용 거의 없음 |
| 보안 | 방화벽·SSH 키로 관리, 클라우드 계정 보안 필요 | 물리적 접근 위험, 다른 용도와 섞임 |
| **권장** | **운영 서버로 권장** | 개발·백테스트 보조용 |

### 7.4 보안 설계 [제안]
- **비밀정보 저장**: 운영 서버에 암호화 파일(sops + age)이나 클라우드 Secret Manager를 쓰고, 실행 시점에만 환경변수로 주입합니다. Git에는 암호화된 파일도 올리지 않습니다(원칙: 운영 서버에서만 생성).
- **로그 마스킹**: 로그 출력 단계에 필터를 두어 `appKey`, `appSecret`, `access_token`, `Authorization` 헤더, 계좌번호, 텔레그램 토큰을 자동으로 가립니다. 요청·응답 원본을 저장할 때도 같은 필터를 거칩니다. 마스킹 테스트를 CI에 넣습니다.
- **접근 권한 분리**: 서비스 실행용 OS 계정(로그인 불가)과 관리자 계정을 분리하고, SSH는 키 인증만 허용합니다. 방화벽으로 들어오는 포트는 SSH만 엽니다(대시보드는 SSH 터널이나 VPN으로 접속). DB 계정은 읽기 전용(대시보드)과 쓰기(엔진)로 나눕니다.
- **키 교체**: KB 키와 AI 키를 교체하는 절차를 문서화하고, 유출이 의심되면 즉시 폐기(토큰 revoke API [확인])합니다.
- **의존성 보안**: 패키지 버전을 고정(lock 파일)하고 secret 스캐닝·취약점 스캐닝을 CI에서 돌립니다.

### 7.5 자동 복구·백업·모니터링 [제안]
- **자동 복구**: Docker Compose(restart: unless-stopped)나 systemd로 프로세스가 죽거나 서버가 재부팅되면 자동으로 다시 시작합니다. 시작은 항상 SAFE 모드에서 합니다(§2.5).
- **DB 백업**: 매일 장 마감 후 DB 덤프를 만들어 암호화(restic 등)한 뒤 다른 저장소(객체 스토리지)에 올리고 30일 보관합니다. 한 달에 한 번 **복구 리허설**을 하고 그 결과를 기록합니다. 시세 원본 데이터(Parquet)는 주 1회 백업합니다.
- **텔레그램 알림 등급**: 정보(체결, 일일 리포트) / 경고(한도 80%, 지연 시세) / 긴급(HALT, 대사 불일치, 결과 불명 주문). 긴급 알림은 확인할 때까지 반복합니다.
- **장애 감지**: 엔진이 1분마다 heartbeat를 기록하고, 별도의 감시 프로세스가 heartbeat 중단, 디스크 사용량, 메모리, 시계 오차(NTP)를 확인합니다. 서버가 통째로 멈추는 경우를 대비해 외부 감시 서비스(무료 등급이 있는 heartbeat 서비스 등)로 "신호가 끊기면 알림"을 받습니다(서비스 선택은 [미확인]).
- **텔레그램 명령**: `/status`, `/halt`, `/resume`(사유 필수), `/positions`. 명령은 등록된 사용자 ID에서 온 것만 받습니다.

## 8. 기타 위험
- **시간대**: 모든 시각은 UTC로 저장하고 표시할 때만 KST/ET로 바꿉니다. 미국 서머타임 전환일, 반일장, 한국·미국 휴일이 겹치는 날을 테스트 케이스로 둡니다.
- **수치 계산**: 금액은 `Decimal`과 통화 타입(Money)으로만 다룹니다. float 사용을 정적 검사로 금지합니다(금액 모듈 한정).
- **명세 변경 감지**: KB 포털의 명세 JSON/Excel을 주 1회 내려받아 이전 버전과 비교하고, 바뀐 API가 있으면 알림을 보냅니다. 명세 파일에 적힌 "최초작성일"이 다운로드 날짜로 바뀌어 있는 것으로 보아 [확인: 2026-10-30로 표시], 날짜 대신 **내용 해시**로 비교합니다.
